# Архитектура CHRONOS 0.2

```
ingestion  ──►  storage (SQLite, миграции, vintages)  ──►  analysis / forecasting / validation
   │                     ▲                                        │
   │                     └──────── knowledge (граф событий) ◄─────┤
   ▼                                                              ▼
 raw cache (SHA-256)                               state (2026) ─► scenarios ─► research ─► UI / CLI
```

| Пакет | Ответственность |
|---|---|
| `chronos.config`, `chronos.logsetup` | Настройки (TOML → env → флаги), структурированные логи (text/JSON в stderr) |
| `chronos.storage` | Схема и миграции (`migrations/*.sql` + Python-миграция баз v0.1), репозиторий рядов |
| `chronos.ingestion` | Коннекторы. Каждый возвращает `IngestBatch`; запись — одна транзакция = один vintage |
| `chronos.timeseries` | Неизменяемые `TimeSeries`/`Panel` с `truncate(origin)` — физическая защита от утечки будущего |
| `chronos.forecasting` | Baseline-модели и модель аналогов (k-NN, точный порт v0.1 + улучшения) |
| `chronos.validation` | Walk-forward, метрики, DM-тест, эмпирические интервалы, панельная проверка, реестр экспериментов |
| `chronos.analysis` | Структурные сдвиги, похожие траектории, многомерные аналоги, лестница причинной доказательности |
| `chronos.knowledge` | Граф: события, источники, механизмы, утверждения, альтернативы, факты; правила R1–R7 |
| `chronos.state` | Модель состояния мира на опорный год с явной «свежестью» каждого показателя |
| `chronos.scenarios` | Условные сценарии (TOML): допущения, механизмы, чувствительность, сигнальные индикаторы |
| `chronos.research` | Исследовательские досье (пример: печать / интернет / генеративный ИИ) |
| `chronos.ui` | Streamlit-интерфейс |

## Ключевые решения

**Vintages вместо перезаписи.** `series` (что измеряем) → `series_vintage` (какие загрузки содержали ряд) → `observation` (значения, хранятся один раз для каждого уникального набора). Повторная загрузка без изменений не пишет строк; изменение значений создаёт новый набор, старый остаётся. `chronos revisions` показывает пересмотры. `as_of_date` позволяет загрузить архивную версию и провести real-time backtest; без неё отчёт явно пишет `revision leakage: PRESENT`.

**Один ряд = один датасет издателя.** Нельзя «склеить» значения из разных датасетов в одном ряду; нельзя смешать REAL и SYNTHETIC под одним именем.

**Статус каждого наблюдения:** `observed | estimated | imputed | interpolated | projected | filler | derived`. Например, у Seshat импутированные значения и «заполнители» столетий помечены и исключаются из оценки прогнозов.

**Валидация не может «подсмотреть».** Модель получает только `series.truncate(origin)`; тест `test_leakage.py` для каждой модели проверяет, что прогноз не меняется при искажении данных после origin. Эмпирические интервалы строятся только из ошибок, исход которых был известен к origin.

**Вердикт пишет машина, а не автор.** Если кандидат не обходит лучший baseline, отчёт так и пишет («prefer the baseline»); если обходит, но DM-тест незначим — сообщает и это; при < 10 неперекрывающихся окнах — «statistically fragile».

**Причинность — лестница, а не ярлык.** T1 ассоциация → T2 предсказательная зависимость (Granger) → T3 условная ассоциация (двусторонние FE, кластерные SE) → T4 квазиэксперимент (stacked event study, пре-тренды, перестановочный плацебо). Каждый уровень сообщает, чего он НЕ доказывает. Гипотезы регистрируются до проверки; все тесты логируются, p-values корректируются по Benjamini–Hochberg по всему реестру.

**Граф знаний не повышает доказательность сам.** Уровни 0–5 — оценка куратора; правила запрещают уровень ≥ 3 без поддерживающего источника, ≥ 4 без научной публикации, «последовательность» с уровнем > 0, следствие раньше причины.

## Миграция на PostgreSQL

SQL-миграции используют переносимое подмножество (кроме `INSERT OR IGNORE/REPLACE` и `ON CONFLICT`, которые есть и в PostgreSQL в форме `ON CONFLICT`). Слой доступа — `sqlite3` с параметризованными запросами; для PostgreSQL нужно заменить `storage/db.py` (соединение, `?` → `%s`) и адаптировать 3 SQL-файла.
